## V2 improvements

Three targeted changes were made between V1 and V2. No ground truth was modified.

| Change | Effect |
|--------|--------|
| Refined system prompt: explicit scalar-shape rule with example | Eliminated scalar-shape SQL errors |
| Improved `json_object()` parser: strips `<think>` blocks and markdown fences | Recovered responses from thinking-mode models |
| Retry error message extended with `LIMIT 1` hint | Reduced repeat failures on the same SQL shape |

**V2 smoke result (same 5 questions):**

| Metric | Value |
|--------|-------|
| Correct | 5 / 5 (100%) |

### Summary of 31 incorrect answers

The failures fall into six recurring patterns. No single-line fix resolves all of them; each requires a targeted intervention.

#### 1. String vs. date type mismatch (5 failures)
Questions that expect a date-formatted string (e.g. `"2026-01-15"`) but ground truth is typed `string`. The model correctly returns the right value as `type: "date"` and the evaluator rejects it because `pred_type != gt_type`. The values themselves are correct.

Affected: `cafe_19`, `pharma_19`, `rest_14`, `elec_18`

#### 2. Table column naming mismatch (6 failures)
The model's SQL aliases the aggregation column differently from the oracle SQL (`"doanh_thu"` vs `"tong_doanh_thu"`). The evaluator compares column names case-insensitively but requires an exact match. All rows and values are otherwise correct.

Affected: `cafe_18`, `pharma_15`, `rest_13`, `fash_06`, `fash_20`, `elec_13`

#### 3. JOIN abstention (10 failures)
Questions requiring a JOIN between two tables (e.g. `sales JOIN catalog ON ma_sp`) cause the model to abstain after two failed attempts. The model either generates an incorrect table name or produces a 2-column scalar result.

Affected: `elec_03`, `elec_04`, `elec_12`, `elec_13`, `elec_15`, `rest_09`, `rest_10`, `fash_09`, `fash_11`, `pharma_14`

#### 4. Percentage representation (1 failure)
`pharma_10`: The model divides by 100 internally, returning `0.2778` instead of `27.78`. The rulebook specifies returning the real number (e.g. 35.5 for 35.5%), but the model interpreted this differently.

#### 5. Answerability calibration (1 failure)
`cafe_21`: "Chi phí nguyên liệu tháng 1?" — the model fabricated an answer (1,756,000) instead of returning `unanswerable`. The required column does not exist in the schema.

#### 6. Semantic SQL errors — wrong filter or aggregation (8 failures)
- `cafe_06`: Revenue on 2026-02-14 — model sums all transactions including cancelled ones (no `trang_thai != 'huỷ'` filter for the café schema which does not have a status column).
- `cafe_14`, `cafe_15`, `cafe_17`: Incorrect window or aggregation scope.
- `pharma_13`: Paracetamol units across two months — model only counted month 1.
- `rest_20`: Most-booked customer — wrong due to tie-breaking ORDER.
- `fash_10`, `fash_15`: Type/value confusion on fashion queries.

## Reproducibility

To re-run the full benchmark on the same hardware:

```bash
python3 eval/evaluate.py \
  --backend transformers \
  --model-path /path/to/Qwen3-14B \
  --out eval_results/my_run
```

Results are written to `eval_results/my_run/summary.json` and `eval_results/my_run/per_question.jsonl`.

The reference V2 results are preserved in `eval_results/qwen3_full/`.
